01 · three requests

Three things you might ask
git to do

These are three ordinary requests. Git can attempt all three, but whether it succeeds cleanly depends on what else happened to the surrounding code — which is what this talk is about.

02 · what git gives you

git's unit is the commit, not the function

git records a commit as a diff of lines against the previous commit; it has no idea a function is a unit at all. So when the retry wrapper is squashed together with a dozen unrelated edits, revert can only take the whole commit, not just the wrapper.

03 · the change

Give each function its own
version history

Instead of one diff per commit, sgt gives each function, class, or method its own chain of versions, oldest to newest. When one function's code refers to another, that's recorded directly — slugify() depends on Config, which depends on parse().

04 · what "current" means

A state is one version
picked per function

You can't pick an old slugify() without also having the Config it was written against, so a state has to respect what depends on what. Everything built on top of a function is its up-set; everything underneath it that it needs is its down-set — those are the two directions revert and cherry-pick move along.

05 · case A — undo

Undo the retry wrapper: drop it
and its up-set

Reverting the retry wrapper means dropping it and everything built assuming it exists — the wrapper, fetch(), sync(), and poll(). What's left still has exactly one version per function, so it compiles and runs like any other state.

06 · cases B & C — look back, move a fix

Pin an older version, or bring
in what a fix needs

Looking at last week's slugify() means pinning an older version on just its own chain — nothing else moves. Moving a hotfix to the release branch means adding that fix's version plus its down-set, whatever it needs underneath to actually compile.

07 · where operations come from

Reading one commit at the
function level

sgt reads a commit after it happened and diffs it function by function instead of line by line. It then splits that diff wherever the changed functions don't call each other, so the retry wrapper and an unrelated rename in the same commit become two separate operations.

08 · surviving squash & rebase

The same change gets the same id

An operation's id is computed from what it changed — which function, what it now contains, what it depends on — not from the commit's SHA. A squash merge, a rebase, and a teammate's separate commit that all produce the same change collapse into one operation with three witnessing commits.

09 · the one case that needs a person

Two edits to the same function
fork its chain

If two people edit the same function at the same time, its chain forks into two versions, and sgt won't silently combine them. It surfaces the fork directly and asks for one new version that supersedes both, and that version only lands if it builds and passes tests.

10 · zooming out

Naming a group of operations
is just a label

On top of all these operations, sgt keeps a small tree of named groups — five to nine at each level — so "what does this codebase contain" has an answer besides reading every file. Renaming, merging, or splitting a group changes the label; it never touches a byte of code.

11 · how it's wired

Reading commits in, writing
a state back out

get reads your commits and mines them into operations; put takes a chosen state, writes it to the working tree, and commits it as one more commit, so git stays the only place bytes live. The round-trip between them works today on this repo's own history; how well the automatic parts — untangling, dependency detection, feature grouping — hold up on a large, messy codebase is still being measured.
