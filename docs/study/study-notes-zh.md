# 研究執行筆記（中文）

給主持人（facilitator）看的操作手冊。從零開始到跑完一位受試者，需要碰到的東西全在這裡。
英文版在 `running-the-study.md`，這份比較精簡。

**兩份如果有衝突，以英文版為準**（答案卷、評分指令、四個階段的內容都寫在那裡，
以及 `participant-materials.md`）。這份中文版每次改設計後都要跟著改，很容易落後。

**兩個網址，記這兩個就好：**

| 角色 | 網址 |
|---|---|
| 主持人（你） | `https://sem-git.firebaseapp.com/admin` |
| 受試者 | `https://sem-git.firebaseapp.com/p/<他的 code>` |

## 這個研究在比什麼

同一個人做兩輪，中間換專案也換工具：

- 一輪用 **plain git**（baseline，對照組）
- 一輪用 **sgt**（我們的工具，實驗組）

任務時段裡**沒有** AI 助手，兩邊都沒有。受試者從頭到尾**不知道**哪個是我們的工具——
畫面上只叫 **Setup A** 和 **Setup B**。

每一輪是**四個階段**：認識這個專案（5 分鐘）、找出造成數字錯誤的那份工作（4）、
把那份工作拿掉（4）、再放回去（4）。每個階段都以 `./stage N` 開頭，
它會把專案重設成該階段的起始狀態——所以某個階段做壞了，**不會影響到下一個階段**。
每個階段做完之後有幾題不計時的問題和一兩句評分陳述，一輪連同作答大約 21 分鐘。

計時開始之前先在同一個專案上不計時地練習一次，讓受試者先摸熟工具。

> 📌 **2026-09-01 的改動：** 第 1 階段以前是「把 AI 助手剛剛改的東西記錄進歷史」，
> 現在換成「認識這個專案」。原因有兩個：pilot 受試者到了第 2 階段還不知道那個網頁在顯示什麼，
> 於是把四分鐘花在搞懂產品而不是找工作，而這個成本會一路壓到後面每一個階段；
> 另一方面那個階段本來的量測早就只剩一份清單了。
> 代價是這個研究現在完全不會用到 `sgt save` 或 `git commit`——
> 這一點寫在 `protocol-v2.md` 第 11 節。

12 位受試者分成 4 個 counterbalancing group（工具順序 × 專案順序交叉平衡），
而且是輪流指派的，所以就算只招到 8 位，每組還是 2 位，資料依然平衡。

正式流程大約 90 分鐘，含休息請抓兩小時。

## 第一部分：整個研究只做一次的事

全部在 `/admin` 的 **Setup** 分頁操作。

### 1. 登入管理介面

用 Google 帳號登入。`ryanyen2@mit.edu` 已經寫在權限檔（`firestore.rules`）裡，不需要額外設定。

要加其他管理員：**Setup → Who else can see this console**。
⚠️ 加進去的人看得到全部受試者資料**和答案卷**。

### 2. 上傳答案卷

**Setup → Answer key → Load answer key JSON**，選 `docs/study/answer-key.json`。

裡面包含兩個測試專案的完整歷史、兩份會被計分的清單（第 1 階段和第 3 階段，
第 2 階段跟第 3 階段用同一份）、第 2 階段可以接受的所有答案字串，
以及第 3、4 階段要比對的頁面清單
（`requestKeys.r1.choices`）、以及第 2、3 題的評分 rubric。
**故意不編進網站程式碼裡**——題目本身會打包進受試者下載的網站，
如果答案跟題目放在一起，受試者打開開發者工具就看得到。

⚠️ **沒載入答案卷的話，那兩份清單完全不會被計分**——會顯示為「未評分」而不是「答錯」
（這是刻意的：答案卷還沒載入時作答，跟三題都答錯是兩回事），但圖表會少一塊。

### 3. 設定 API keys

**Setup → Session keys**，三個欄位：

| 欄位 | 用途 |
|---|---|
| Anthropic API key | 給 Claude Code（AI 助手）用 |
| OpenAI API key | 給 sgt 的自然語言選取和 feature 自動命名用 |
| Model id | 整個研究固定用同一個模型 |

重要事項：

- **一定要開專用 key 並設 spend cap（花費上限）。絕對不要用你自己的 key。**
- 受試者的電腦在安裝時會自動從伺服器抓這兩把 key，所以他們**不需要自己貼 key**，
  也**不會用到自己的帳號額度**。
- 每位受試者做完後：在 Participants 分頁按 **Revoke** 標記為已撤銷，
  然後**去 OpenAI / Anthropic 的後台也真的把 key 撤銷**
  （網站上的按鈕只是更新狀態標記，並不會真的停用 key）。

### 4. 填寫受試者看得到的文字

**Setup → Participant-facing settings**：聯絡 email、報酬說明、IRB protocol 編號、
知情同意書（consent form）說明。

下面還有四個 bundle 下載連結欄位，**通常留空就好**：`make-study-bundle.sh` 會直接寫進
網站自己的靜態檔案，部署後 bundle 就已經在 `/bundles/study-<專案>-<a|b>.tgz`，
而那正是安裝頁去抓的位置。只有在你要把 bundle 放到別的地方時才需要填。

⚠️ **bundle 檔名不能出現 `sgt` 這個字**——受試者看得到下載網址，看到就知道哪個是實驗組了。
目前的檔名格式是 `study-<專案>-a.tgz` / `-b.tgz`（專案是 `bikecount` 或 `footfall`），
a 和 b 不會洩漏哪個對應哪個條件。

⚠️ **每次重建 bundle 之後，答案卷要重新產生再上傳一次。** bundle 的建置流程最後會跑
`sgt log --rebuild`，feature 和 group 的 id 都會變，舊的答案卷會把每個人都算成答錯。
指令在英文版 `running-the-study.md` 的「Load the answer key」那一節。

### 5. 建置 bundle 並發佈（一個指令搞定）

```bash
scripts/publish-study.sh
```

這個指令會依序執行：建置四個 bundle → 建置網站 → 部署上線 → 從線上下載回來比對檔案大小，
確認受試者現在下載到的就是剛剛建的版本。

> ⚠️ **常見誤解，很重要：**
>
> `npm run build && firebase deploy` **不會**重建 bundle。
> `npm run build` 建的是**網站本身**；bundle 是四個獨立的 `.tgz` 壓縮檔，
> deploy 只是順手把 `web/public/bundles/` 裡**已經存在**的檔案一起送上去。
>
> 所以如果你改了 sgt 的程式碼然後只跑 deploy：**網站是新的，但受試者下載到的工具是舊的**，
> 而且畫面上完全看不出差異。`publish-study.sh` 就是為了讓這件事不可能發生。

bundle 只有四個（git × 2 專案 + sgt × 2 專案），不是每位受試者各一個。
「這個人是哪一組、他的 API key 是什麼」是安裝腳本用受試者的 code 去伺服器查的，
所以同一個 bundle 可以重複給不同人用。

建置時會自動執行：
- 跑測試（沒過就拒絕打包）
- 預熱 sgt 的歷史檢視（這樣受試者的第一個指令不會卡住好幾秒）
- 釘住兩邊編輯器的擴充套件版本
- 附上一個**跟兩個正式專案都不一樣的**練習用 repo

⚠️ **練習 repo 那幾行輸出要看一下。** sgt 條件下，建置腳本會把四個 feature 的名字
釘死（The Cart / Discounts / Receipts / Shipping），然後逐一檢查練習單上引用的每一個
handle。如果它警告某個名字沒釘上、或某個 handle 找不到，代表**那台機器上的練習單是錯的**，
受試者會當著你的面撞到。在正式開始前處理掉，不要等到 session 中間。

⚠️ **如果有未 commit 的改動，這個指令會直接拒絕執行**——
否則 bundle 裡打包的版本會標成 `-dirty`，之後就無法回答「P07 跑的是哪一版」這種問題。

只改了網站上的文字、不需要重建 bundle 的話：`scripts/publish-study.sh --site`。

### 6. 建立 12 位受試者

**Participants → Create 12。**

一次生成 12 筆紀錄，自動輪流分派到 4 個 counterbalancing group。
每人會拿到一組 24 字元的 code，**這個連結本身就是他的密碼**，要當密碼看待。

招募到人之後，把 email 填進該列（每格會顯示是誰的，例如 `P03 email`），
然後複製該受試者的專屬連結寄給他。

> 📌 **系統不會自動寄信。** email 欄位只是紀錄用途，邀請信要你自己寄。
> 但還是要填對——之後 consent 確認、報酬發放、資料追蹤都靠這一欄對人。

## 想先試跑？用 pilot，不要用正式受試者的名額

**Participants → Add pilot** → 會產生 `X01`（不是 `P01`）。

跟正式受試者**完全一樣**：真的連結、真的 API key、真的 bundle、真的 telemetry。差別只有：

- ✅ 不會出現在 Results 分頁（除非你勾選 *Include the pilot records*，勾了整頁會出現警告提示）
- ✅ 不會算進 12 人的名額和組別平衡
- ✅ **不管你跑過幾個 pilot，`Create 12` 產生的永遠是 P01–P12**
- ✅ 受試者的頁面上每一步都有 **rehearsal** 標籤（萬一發錯連結，他自己就看得出來）
- ✅ 開過之後還可以刪掉（正式受試者一旦開過連結就不允許刪除）

用 pilot 來測試那些「只有在正式環境才會出問題」的東西：
Google 登入流程、bundle 下載、API key 有沒有真的傳到受試者的電腦上。

如果連資料庫都不想碰，可以用 emulator 模式（見英文版 `running-the-study.md` §6），
畫面上會有橘色的 "Rehearsal mode" 橫幅提醒你。

## 第二部分：每位受試者的流程

### 前一天：把連結寄給受試者

自己寄信，內容大概是：

> 我們約的時間之前，麻煩先開這個連結，把前面幾頁做完：一份知情同意書、幾題背景問卷、
> 還有一個安裝步驟。安裝大概需要幾分鐘，它會自己下載需要的 Python，
> **不會動到你電腦上其他任何東西**。
> 做到「練習」那一頁就停下來等我們開始。
> 如果有任何一項檢查變成紅色，**直接跟我說，不要自己試著修**——
> 我們在正式開始前處理掉比較省事。

**要給受試者的東西只有兩樣：**
1. 他的專屬連結：`https://sem-git.web.app/p/<code>`
2. 上面那段說明

其他所有東西（bundle 下載、API key、操作指令）他都會從網頁上自動取得。

安裝步驟的最後有一個自動檢查清單，會逐項打勾或標紅：
Python 版本、專案測試是否通過、歷史工具是否就緒、Claude Code profile 是否隔離、
API key 是否到位、**以及一次真正的 AI 呼叫測試**。
最後這項是重點——它能抓到「key 有填但其實是錯的或過期的」這種問題。

### 當天：把 Live 監控分頁開著

**Live** 分頁會即時顯示每位受試者的狀態：
- 目前在哪一步
- 目前這題的倒數計時
- 瀏覽器有沒有連線
- **電腦有沒有在回報 telemetry**
- 最近 24 筆操作紀錄

| 狀況 | 處理方式 |
|---|---|
| 「their machine」指示燈變紅 | 請受試者確認 session shell 還開著，然後跑 `study-sync`。資料不會遺失，只是你暫時看不到最新動態。 |
| 中途被打斷或出事 | 請受試者按 **Pause the clock** 並選擇暫停原因。分析時用的是實際作業時間，暫停的時間不算。 |
| 連結打不開了 | 清了瀏覽器快取、換瀏覽器、或用無痕視窗都會觸發鎖定（防止同一個連結被兩個人同時使用）。打開該受試者的紀錄 → 按 **Release link** 解鎖。 |
| 有指令執行失敗 | Live 卡片上會直接顯示紅色的失敗指令（這是 pilot 03 之後加入的功能）。 |
| 要讓某人**重新開始** | 名冊每一列都有 **Reset** 按鈕：清掉該受試者做過的所有資料，但**連結和條件分配順序不變**（維持 counterbalancing 平衡的關鍵），回到第一步重新來過。 |
| 建錯了要**完全刪除** | 同一列的 **Delete** 按鈕：連人帶資料整個移除，連結永久失效。 |

> Reset 和 Delete 兩個都會先**列出將要刪掉的資料數量**
>（例如「1 responses, 5 events, 1 scoring」）再要你確認。
> 兩個按鈕在**任何狀態**下都能使用——舊版只有 `created` 狀態才能刪，
> 導致一個已經簽過 consent 的測試帳號完全無法刪除。
>
> 要一次清空所有測試資料（例如正式開跑前清掉 pilot 資料）：
> 展開 **Danger zone**，有「只刪 pilot」「只刪正式受試者」「全部刪除」三個選項。

### 資料會不會遺失？

不會。問卷答案、任務回答、訪談筆記都是**每打一個字就先存到瀏覽器本機**，
再用 debounce（延遲合併）寫進資料庫——關分頁、重新整理、瀏覽器當機、網路斷線，最多掉最後一個字。

唯一「不會自動寫進資料庫」的是**主持人的評分**：評分是判斷行為，
半完成的 rubric 不應該進正式資料。它會暫存在你這台電腦的瀏覽器裡，
下次打開那一題時會問你要不要還原上次的進度。

**主持人在場時不變的事：**
- **過一半**和**剩兩分鐘**的時候要口頭報時（第 1 階段 5 分鐘，其餘三個各 4 分鐘，
  報一次就好，報「剩兩分鐘」）
- 常提醒受試者「我們在測這兩套工具，不是在測你的能力」
- 鼓勵他持續講出自己在想什麼（think aloud protocol）

### 做完之後

1. 在 Participants 分頁按 **Revoke** 標記 key 已撤銷，**然後去 API provider 的後台真的把 key 停用**
2. 請受試者在 session shell 裡跑 `study-sync --final`，再跑 `study-cleanup`
3. 進入該受試者的 **Requests & scoring** 頁面進行評分

## 第三部分：評分

開啟某位受試者的紀錄 → **Requests & scoring**。

每一題會顯示：受試者做了什麼操作、花了多久、有沒有超時、他的作答，
旁邊並排顯示標準答案供對照。

**第 1、2 階段不用你評清單那部分。** 兩個階段最後都是同一份十一項的清單，
主控台會拿答案卷算 set F1，並用旁邊的信心程度算出 calibration（信心減去答對比例）。
如果畫面顯示未評分，代表答案卷沒載入。

第 1 階段問的是「歷史裡**最新的那一份工作**影響了哪些部分」。
答案是首頁的兩樣東西（最忙的一天那個數字、最近兩週的長條圖），兩個專案都一樣，
十一項裡只中兩項——所以全部都勾大約只有 0.31 分，這一題是真的能分出高低的。

第 2 階段還要你評「他找到的是哪一份工作」。主控台會把他的答案跟答案卷可接受的字串並排顯示
（兩套工具的講法都收，commit sha 和 group 名稱都算對），你判斷。
那份清單很長是故意的，但它不能取代你當場聽他怎麼說。

**第 3、4 階段要跑評分腳本**，把輸出**原封不動貼回**對應欄位（這是分數的證據）：

```bash
# 第 3 階段：該拿掉的拿掉了，其他頁面沒被動到
python3 scripts/study/score_dashboard.py ~/study/p07/work \
    --expect ~/repos/sgt-study/footfall/.study/removed-pages \
    --target-pages hourly,monthly,overview,sides,yearly

# 第 4 階段：每一頁都回到移除之前的樣子
python3 scripts/study/score_dashboard.py ~/study/p07/work \
    --expect <移除之前的 snapshot>
```

腳本會分開回報三件事，**不要把它們混在一起看**：程式跑不跑得起來、
該變的頁面有沒有變、其他頁面有沒有被弄壞。第三件才是這個研究真正在問的。
`--target-pages` 兩個專案不一樣：footfall 是 `hourly,monthly,overview,sides,yearly`，
bikecount 是 `hourly,monthly,overview,years`（bikecount 的年度頁在 `/years`）。
兩份清單都在 `answer-key.json` 的 `s3.markers` 裡，照那裡讀，不要照這裡背。

**每一輪之後的兩份問卷**（工作負荷 NASA-TLX、易用性 UMUX-Lite）不用你評，
受試者填完就直接進分析。

> ⚠️ **NASA-TLX 這一份，主持人不要多嘴。** 它是在一排刻度上點選，畫面上**不顯示數字**；
> 六題裡有一題（Performance 表現）兩端方向和其他五題相反——左邊是 Failure、右邊是 Perfect。
> 這是原始量表本來就長這樣，不是 bug，畫面上也已經標示出來。受試者問的話，
> 指著線兩端的字讓他自己讀，**不要告訴他哪一端算「好」**，那等於替他作答。

> 📌 這裡以前還有一份五題的記憶測驗和三分鐘的口述摘要，2026-08-17 拿掉了。
> 它們一場要花十二分鐘，而且是在受試者剛好用完時間的當下，要他關掉專案、憑記憶用寫的回答。
> 結果是**兩個評分者之間的差異比兩個條件之間的差異還大**。理由寫在 `protocol.md` §5.6。

**最後的「比較兩套工具」問卷**也是主控台自己跑：七題他剛剛真的做過的工作、
為什麼有差別、兩個「哪種情境下值得用」的假想題、整體偏好，以及「什麼會讓你不想用」。
其中「哪一邊比較好」那十題（七題工作 + 兩題情境 + 整體）都是同樣五個選項——
**A 明顯 / A 稍微 / 沒有明顯差別 / B 稍微 / B 明顯**。
「沒有明顯差別」是一個**真正的答案**，該是這個答案的時候就讓它是，不要把人往兩邊推。
（分析時會依照該受試者的 sgt 是 A 還是 B，把答案換算成 −2…+2；中間值一律照實回報，
不會當成缺答刪掉。）

**Interview** 分頁是訪談題目加逐字筆記的空間。

> ⚠️ 第四題「你希望能問這段歷史什麼問題？」**一定要在受試者比較兩套工具之前問**。
> 兩次 pilot 裡，受試者在這題都講出了非常接近 sgt 核心功能的想法，
> 其中一位甚至是在 git 那一輪就這樣講的。如果問的順序錯了，這個發現就浪費掉了。

## 待決定事項（需要在第一位受試者之前處理）

### 🟢 `Sgt-Op` commit trailer 問題（已處理到可以開跑，但要在論文裡揭露）

sgt 條件的專案裡，每個 commit 訊息底下都掛著一大串操作編號。實測 footfall 最新的那個 commit，
作者寫的訊息只有六行，底下跟著 **125 行** `Sgt-Op:` 的 hex；整個 sgt 條件的歷史共 2,050 行。
git 條件的專案在製作時就沒有這些。

這些 trailer **不能直接刪掉**：resync 和 sync 會讀它們，把它當成「這個 commit 內容是什麼」
的證據。所以做法是改 git 的 pager：**兩個條件都設一樣的**
`core.pager` 過濾掉「整行只有 `Sgt-Op:` 加一串 hex」的行
（`scripts/study-bundle/install/setup.sh`）。134 行變 12 行，作者寫的字一個都沒動。
git 條件本來就沒有這種行，所以同一份設定在那邊是空操作——**因此這不是條件差異**。

還沒蓋到的部分：editor 自己的 git 介面是自己算訊息的，不走 pager，sgt 條件的受試者
打開它還是會看到全文。這一點寫在 `protocol-v2.md` 第 11 節的 limitations 裡。

### 🟡 其他待處理事項

- **API key 的時間點問題：** 建好 12 位受試者**之後**才改 API key 的話，新的 key
  不會自動傳到已建立的受試者身上。需要逐一按 **Re-issue** 重新發放。
  而且 Revoke → Re-issue 這條補救路徑**從來沒有人真的測過**——先用 pilot 帳號測一次再說。
- **兩個專案的同構性問題：** 兩個專案用的是同一套 episode 劇本（只是替換了名詞）。
  pilot 受試者反映第二輪「明顯在套第一輪的模式」。
  設計上已經用 counterbalancing 處理了順序效應，
  但分析時一定要把 **order（順序）當作固定效果**納入模型。
  在 12 人的小樣本下，這個 carry-over effect（前一輪的影響）
  可能比條件本身的效果還要大——這必須寫進分析計畫，不能事後才補充。

## 詞彙對照表

| 英文 | 在這個研究裡的意思 |
|---|---|
| condition | 兩種工具之一（git 或 sgt） |
| block / half | 一輪作業時段，四個階段加作答約 21 分鐘 |
| counterbalancing group | 決定工具順序和專案順序的分組編號（1–4） |
| bundle | 發給受試者的壓縮檔，解壓縮後就能直接使用 |
| stage / 階段 | 一個任務段落（s1–s4）。每個都用 `./stage N` 重設起始狀態，各自獨立計時 |
| feature | sgt 把專案切出來的一個部分，在 `sgt log` 裡是一列（lane） |
| checkpoint | 一個 feature 上的一段工作，在那一列上是一個方塊 |
| group（◆） | 一次跨好幾個 feature 的工作，`sgt log` 畫在下面那幾行 ◆。第 3、4 階段要動的就是它 |
| pilot / rehearsal | 試跑用的模擬受試者（編號 X01、X02…），不計入正式結果 |
| telemetry | 受試者電腦自動回報的操作紀錄資料 |
| answer key | 答案卷和評分標準的合集 |
