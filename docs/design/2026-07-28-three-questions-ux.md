# The three questions: a user-model-first redesign of sgt's surfaces

Date: 2026-07-28. Scope: CLI, TUI (`sgt log` + consequence pane), VS Code extension.

## The problem, from the user's chair

A user working in an sgt repo needs three questions answered at all times:

1. **What did I do?**
2. **What can I do next?**
3. **What happens if I do it?**

Today each answer exists somewhere, but as *surfaced information*, not as design. Running the
current tool against this repo's own store shows where each answer breaks down:

- **Labels don't hold memory.** Three different groups in `sgt log` all render as
  "DecisionClash DecisionEdge DecisionGraphVie…". Feature labels are word salads of symbol
  names, generated by an LLM at map-build time, and the user is never asked, never shown a
  label at the moment they save, and never told when their mental name for the work diverges
  from the tree's name. Users encode memory *at save time, by message* — but the label the
  system will file the work under is invented later, silently, from symbols. The mismatch is
  discovered weeks later, when nothing in the graph matches anything the user remembers doing.
- **Ops leak everywhere.** Headers ("2170 op(s)"), row trailers ("· 163"), previews
  ("removes 16 op"), fallout tables (op-id[:12] rows). Ops are the kernel's internal currency —
  the user's units are saves, features, symbols, and files. Density is the only op-derived
  signal a user needs, and the sparkline already carries it.
- **Consequences are shown in kernel language.** `▸ [0███] @0 Merge feat/semantic-u ░░░ · 16
  op removed` answers "what happens next" only for someone who already knows what a car, a
  checkpoint index, and the dim field are. Worse, the *interesting* case explains nothing:
  revert v2 → save v3 → restore v2 previews as "restores 0 op · 0 file(s) changed" — a silent
  no-op, because v3 is the live tip and restoring v2 would fork the symbol. The user's actual
  question ("I thought this was like a rebase?") is answered with an empty set.
- **Refs are typed, not selected.** Full 64-hex feature ids appear in `log --tree` and in every
  preview header, while six different resolvers already accept minimal unique prefixes. The
  display doesn't teach the input: the grid brightens the unique prefix (good), everything else
  prints 8/12/14/64 chars inconsistently.
- **Stale affordances.** Error hints route to removed verbs (`sgt map`, `sgt get`). `restore`
  cannot resolve the very op id `revert` just printed (its resolver only searches the ideal —
  and the op being restored is by definition not in it).

## Ground truth the design must teach (verified against the kernel)

- History is a **partial order**: per-symbol content chains (`before → after` hashes) plus
  `requires` edges. No op has a timestamp; the timeline axis is just git commit order.
- The current state is a **subset** (ideal) of an immutable store. Verbs never rewrite; they
  re-select. Every mutation lands as a forward git witness commit.
- `revert X` = drop X and everything above it. `save` after a revert extends the *surviving*
  tip — so the new work looks linearly "rebased on top", while the reverted version remains in
  the store as a **ghost sibling** of the new tip.
- `restore` of a ghost whose symbol has a different live tip is *invalid* (two live versions =
  fork), so the kernel refuses/filters it. It is neither a fork-on-restore nor a rebase: it's
  **one live version per symbol; everything else waits as a ghost**. The correct affordances
  when blocked are **swap** (revert the live tip, then restore the ghost) or **reconcile**
  (`sgt resolve <symbol>` → merge-op).

## Design principles

1. **Saves are the user's anchors; features are the folders; ops are invisible.** Every
   human-facing surface is stated in saves (commit message + short sha), features (label +
   minimal-unique prefix), symbols, and files. Op *density* stays as the sparkline/shading.
   Op ids and counts move behind `--json` and `sgt advanced`.
2. **Feedforward at the moment of encoding.** The moment a user saves is the only moment the
   label can enter their memory. `sgt save` must answer, in its output: *which feature(s) did
   this save's work land in, under what name?* — and give an immediate, one-flag way to correct
   the name (`--as`), because authored labels permanently win over LLM labels.
3. **Every consequence is a before → after morph plus one plain sentence.** No new jargon in
   output. Refusals explain the rule they enforce and name the two commands that unblock.
4. **The display teaches the input.** Anything printed as a handle is exactly what the user can
   type back: the minimal unique prefix, brightened. One canonical short width (8) elsewhere.
5. **Answers ranked by question.** `sgt log` opens with "what I did" (the rail, newest first,
   feature-chipped). The map (lane×commit grid) is the spatial overview: `sgt log --map`.

## The changes

### C1. `sgt save` becomes the labeling moment (CLI)

After the witness commit, render the attribution the ledger already computes (today the
result of `assign_at_save` is discarded):

```
✓ save 9fba02a "get_cached v3: containment check"
  → caching layer (0289)   get_cached · 1 symbol
  → retry policy (1acf)    +2 symbols
  ⚠ 1 symbol landed in a feature with a provisional name — name it: sgt save --as "<label>"
```

- `sgt save --as "<label>"` names the save's dominant feature (authored LWW register; wins
  permanently). If the save created a new lane, `--as` names it at birth.
- A save that scatters across ≥3 features gets a gentle mismatch warning (the "is this what
  you meant to do?" feedforward) with the regroup hint.

### C2. Ops disappear from human output (CLI + TUI)

- Header: `65 features · 232 saves · 24 subsystems` (op count dropped).
- Grid rows: sparkline stays; trailing `· 163` op count dropped; checkpoint chips stay.
- Rail rows: `· N op` dropped; replaced by **feature chips** — the labels of features touched
  by that save (derivable from provenance), which is also the commit→features mapping asked
  for. Format: `sha message  [caching layer · retry policy]`.
- Tree: minimal-unique prefix instead of full `f-…64hex`; density glyph instead of `· N op(s)`.
- Previews: "removes 16 op" → `removes 2 checkpoints · 3 symbols in 1 file (cache.py)`.
- Fallout table rows: symbol names, not op-id[:12].
- `sgt log --ops` relocates to `sgt advanced ops` (kernel-facing). `--json` shapes unchanged.

### C3. Consequence preview speaks user (TUI graph.py + ideal_edit)

- Header: `▸ revert  "caching layer"  0289  — removes 2 checkpoints, keeps 64 features intact`.
- Checkpoint rows named by their save message slug, marked `✗ removed` / `◐ partially` /
  `· kept`; magnitude bars stay (they're good), `[0███]`-style car glyphs and `@n` indices are
  demoted to a dim suffix (they remain the typeable rewind refs).
- Files touched listed by name (≤5, then `+N more`).
- "dim field" → `· 64 other features unchanged`.
- **Blocked restore becomes a first-class panel** instead of a 0-op preview:

```
✗ can't restore get_cached v2 — a newer version is live
  cache.py::get_cached has one live version at a time; v3 (save 9fba02a) is live,
  v2 (save 4cbf2e7) is a ghost behind it.
    swap      sgt revert 9fba02a && sgt restore 4cbf2e7   — put v2 back, park v3
    combine   sgt resolve cache.py::get_cached            — reconcile v2 + v3 into one
```

### C4. Refs: prefixes everywhere, resolvers symmetric (CLI)

- `restore` resolves op ids against the **whole store** (the ghost being restored is never in
  the ideal); revert/restore print handles as minimal-unique prefixes and accept them back.
- One canonical short width (8) for sha-ish ids in prose; minimal-unique brightening wherever a
  handle column exists.
- Stale hints fixed: `sgt map` → `sgt log --tree`, `sgt get` → `sgt save`/`sgt log --refresh`.

### C5. Command surface diet (CLI)

- `sgt log` default = rail ("what I did"); grid becomes `sgt log --map` (kept as the spatial
  overview and the extension's default). `--rail` stays as a hidden alias; `--focus`/
  `--timeline`/`--links`/`--at` imply `--map`.
- `sgt log --ops` relocates to `sgt advanced ops` (hidden compat alias kept) — the one demotion
  that shipped. `advanced reindex`/`after`/`suggestions` and `revert --intent` were audited for
  removal but kept: each is a real capability with a caller (fsck's remedy, declared edges, the
  only surfacing of dual-lane conflicts, the keep-dependents intent thread) — deleting them
  would have removed capability, not noise. The help text no longer advertises them beyond the
  `advanced` roster.
- `log --summary` caps list dumps at 5 + `(+N more — --full)`.

### C6. VS Code extension

- Rail view gains the same feature chips per save row; clicking a save row lights the features
  it touched; clicking a lane lights its saves on the axis (commit⇄feature cross-highlight).
- Lane/car text drops op counts (density cells already encode it); inspector shows
  saves/symbols/files instead.
- Editor → graph: "Reveal in Workbench" selects and spotlights the feature owning the symbol
  under the cursor (today the hover link only opens the panel).
- Save card shows the C1 attribution lines after each save (from `save --json`).
- Blocked-restore panel mirrors C3's swap/combine remedies.

## Out of scope (recorded, not attempted now)

- Automatic label quality (better clustering); C1 attacks the encoding moment instead.
- MCP parity for collab verbs; unchanged.
- The `--at`/playhead workflow; unchanged.

## Test impact

`tests/tui/test_graph.py`, `tests/test_so_what.py`, `tests/golden/*` pin today's strings and
will be updated alongside; JS parity tests (`tests/test_graph_layout.py` etc.) unaffected by
text changes but rail chips add fields to `episode` rows (additive).
