§1What sgt is

sgt sits on top of a normal git repository. It watches commits and mines each diff into a set of operations, one per changed function, method, or class. Each operation records which symbol changed, the code before and after the change, and which other symbol-versions it depends on. sgt treats this set of operations as the history. The commit sequence that produced them is just how they arrived.

Git already gives you commits and trees. sgt adds a second, finer index underneath that, built from symbols instead of files and dependencies instead of parent pointers. The commits still exist and still work with any other git tool. sgt's operations are derived from them and can be recomputed from them at any time.

This document walks through the design choices behind that operation layer, covering the unit of history, how sgt recognizes that two edits touch the same thing, what happens when two edits collide, how a merge actually gets computed, and what happens when the automatic parts can't decide something on their own. Git, Darcs, Pijul, jj, and a formal model called lazy merging come up throughout, wherever their design answers the same question sgt is answering. Most of them got there first, and sgt's choices are often a direct reaction to trade-offs they already made explicit.

§2The unit of history is a symbol edit

A git commit stores a whole tree. If ten files changed and only one line in one of them actually mattered, the commit still carries the full state of all ten. sgt's miner reads that same commit, parses the files with tree-sitter, and cuts the diff along symbol boundaries. Each function or method or class that changed becomes its own operation, with its own before and after content and its own list of dependencies on other symbol-versions. A commit that touched three unrelated functions becomes three operations.

Darcs and Pijul made a related move earlier. Both store and reason about a patch instead of a full snapshot. The difference is where the boundary of that patch comes from. A darcs or Pijul patch is whatever hunks a person selected at record time. sgt draws its operation boundary by parsing, so nobody has to decide by hand where one operation ends and the next begins.

jj keeps the commit as its stored unit, but gives each commit a change-id that survives rebases and edits. That's the same instinct, attaching a stable identity to something below the raw content, applied one level up to a whole commit instead of a symbol. Lazy merging's editor transactions are closer to sgt's grain in spirit, since both are drawn automatically rather than by hand. The difference is where the automatic boundary comes from. An editor transaction is grouped at the moment of typing, from paste and autocomplete events. sgt's operation boundary is drawn later, by parsing a diff after the fact.

cost Symbol-level parsing needs a grammar for the language and a file that actually parses. When a file doesn't parse cleanly, sgt falls back to treating the whole file as one symbol, which is exactly git's grain. This happens for generated files, badly formatted files, and languages without a tree-sitter grammar. The fallback is safe, but in that case sgt is not buying anything over a plain commit.

§3A running example

Here is a small case to make the rest of this concrete. A file billing.py has three functions, charge, refund, and apply_discount. A commit C0 introduces all three. sgt mines C0 into three operations, one per function, each with no dependency because each is a first version.

From there, two things happen at the same time. A coding agent opens one commit, C1, that does three unrelated things. It adds a caching helper used by charge, tweaks rounding in refund, and changes the discount tiers in apply_discount. Separately, before pulling C1, Alicia fixes a one-line off-by-one bug directly in apply_discount, working from the same C0 version of that function.

Nothing about this setup is unusual. It's the same thing that happens whenever two people, or a person and an agent, work from the same base and haven't synced yet. The next few sections use these seven operations to walk through what sgt actually does with them.

§4Removing one change

Say the caching helper turns out to be a bad idea and has to go, while the refund and discount changes from the same commit should stay. In git, C1 is one commit, so pulling the caching helper back out means editing the file by hand or splitting the commit after the fact. In sgt, d2a5 is its own operation and nothing depends on it, so sgt drops it directly. e88c and f009, the other two operations mined from the same commit, are untouched.

jj makes this easier than plain git with jj split, which pulls a commit apart into pieces you can abandon separately, but that split is still done by hand, choosing which lines go in which piece. Darcs and Pijul can unrecord a single patch directly, the same way sgt drops d2a5, as long as no later patch commutes past it. If a later patch touches the same lines, that patch has to be unrecorded first. sgt doesn't hit that requirement here because d2a5 has no dependents.

If something did depend on the caching helper, dropping it stops being free. sgt keeps its set of operations downward-closed, so removing one operation also removes everything built on top of it, unless you explicitly ask sgt to keep the dependents and give them something new to build on instead. §8 covers that case.

§5Identity: carried or detected

Two edits can only be recognized as touching the same thing if something ties them together across the edit. Systems solve this two ways. Some carry an identity forward from the moment something is created, so it never has to be re-derived later. Others detect identity after the fact, by comparing content or position.

jj carries identity directly. A change-id is minted once when a commit is created and stays attached to that commit through every rebase and rewrite, even after the commit hash itself changes. Pijul carries identity at a finer grain. Each line gets a vertex identified by the hash of the change that introduced it plus its position, and that vertex identity survives edits happening around it. Lazy merging carries identity through the document's schema, since a cell's position in the schema is fixed and edits to it are tracked against that fixed position.

git detects identity instead of carrying it. A blob's hash is its content, so a renamed file with unchanged content is recognized as a rename only because a heuristic spots the match afterward. Change the content even slightly during the rename and git usually stops connecting the two. Darcs is close to git here. A patch is tied to the exact file context it was recorded against, so a later restructuring can break the commutation check that identity depends on.

sgt also detects identity rather than carrying it. A symbol gets a canonical id the first time it's seen, and later commits are matched against it by a tiered check, an exact hash match first, then a fuzzy match on the body and surrounding context if the hash moved. Renaming apply_discount or moving it to another file still resolves to the same id as long as enough of the body matches. A large rewrite bundled into the same commit as the rename can break that match, and sgt then treats it as a brand new symbol with no history. That's a real gap next to jj's change-id, which survives a rewrite with no matching step at all, because it was never re-derived in the first place.

§6What a conflict is

f009 and g5c2 both list c91d as their required version of apply_discount. That's a fork. Two different next versions were built from the same starting point. sgt detects this by checking for exactly that pattern, two operations claiming the same symbol and the same before-version, and once it finds one, it excludes both operations, and anything built on either of them, from the set it treats as valid history. Neither one wins. Both stay on record as an open fork, and everything else in the repository keeps working normally.

Other systems locate a conflict differently. git's three-way merge finds a conflict only when the same lines are touched on both sides, so if Alicia and the agent had touched different lines of the same function, git would merge them automatically with no conflict at all, whether or not that result was actually correct. Pijul finds a conflict as a shape in its line graph, two insertions with no ordering between them, which can be as fine as a single overlapping line. jj represents an unresolved conflict as a value stored in the commit itself, an algebraic list of the pieces that disagree, and materializes it into the file as ordinary-looking conflict markers so a person can resolve it by editing text. Darcs represents a conflict as its own kind of patch, called a conflictor, that stays in the history until something later supersedes it.

sgt's fork is coarser than all of these because it compares whole symbols instead of lines or byte ranges. Two edits to different lines of the same function still fork in sgt, even in cases where they would merge cleanly under any line-based system. §10 covers that cost directly.

§7How a merge is computed

Once a fork is on record, sgt still has to decide what "current" means for everything that isn't part of the fork. It does this by grounding, which means starting from the set of all known operations and removing anything whose required version never landed. What's left after that pass is the valid set. This is a fixpoint computation over the whole op graph. It considers every operation sgt knows about, not only the two branches that happen to be in front of you at the moment.

Run it over the seven ops from §3. a3f1, b7e0, and c91d have no requirements, so they ground immediately. d2a5 requires nothing either and grounds on its own. e88c requires b7e0, which is already grounded, so it grounds too. f009 and g5c2 both require c91d, and c91d is grounded, but sgt already flagged this pair as a fork in §6, so neither one is added to the valid set. The result is five grounded ops and two excluded ones, sitting off to the side until someone resolves the fork.

Pijul computes the analogous result with a pushout in its category of patches, which produces a new graph state directly from the two branches without ever naming intermediate steps, and proves the result is the smallest state consistent with both. That proof is stronger than anything sgt offers. sgt's grounding pass gives you a valid set and an excluded set. It comes with no proof that the result is minimal or unique, because it works over dependency edges between whole symbols instead of a line-level graph with an established algebra behind it. Darcs computes a similar result by commuting patches past each other one pair at a time, which is exactly why it can blow up combinatorially on repositories with a lot of concurrent history. jj takes a different approach again and does not try to resolve most conflicts automatically at all, it packages the disagreement as a value and lets the working copy carry it forward until a person edits it away. Lazy merging's lattice join is the closest formal cousin to sgt's grounding pass, both compute a result from partial, possibly conflicting inputs without requiring a total order first, though lazy merging's join is defined and proven over abstract cells and never claimed as a fit for real source files.

§8When you have to step outside the algebra

Grounding tells you f009 and g5c2 are excluded. It does not pick one, and it does not write a third version that combines them. Someone has to look at both edits to apply_discount and decide what the function should actually say. sgt's answer for this step is a small set of rewrite verbs. merge-op folds two operations into one, split-op breaks one operation into smaller pieces, transplant moves an operation onto a different base, and revert --keep-dependents undoes an operation while leaving whatever was built on top of it alone. Running merge-op on f009 and g5c2 produces a new operation, hollow rather than mined from a diff, that chains onto one tip's own history instead of pointing at both parents. It never re-triggers the fork check, because the fork check only fires on two operations claiming the same before-version, and a hollow op has no before-version of its own to collide on.

git leaves this same step almost entirely to you. A conflicted merge drops both versions into the file with conflict markers, commits nothing until you edit them out by hand, and records no structured trace of what the two sides actually were once you're done. Pijul stays inside its own algebra here instead of stepping outside it, resolving a conflict by inserting a new patch that supplies an explicit order for the colliding lines, so the resolution is itself a first-class patch subject to the same laws as everything else. jj also stays inside its model, since the conflict is already a value living in the commit, and resolving it is just editing the file until the algebraic representation collapses back to a single value with no listed alternatives. Lazy merging does not attempt this step at all. The paper is explicit that producing a semantically correct merged result is outside its scope, and leaves conflict resolution to whatever system sits on top of the lattice.

sgt's rewrite verbs are the one place in the whole design where a person, or an agent, makes a judgment call that the op graph itself cannot make. Everywhere else in this document, the answer comes out of dependency data alone.

§9Syncing over git

sgt does not run its own server or its own network protocol. Operations, forks, and the metadata around them get pushed and pulled through ordinary git refs, the same transport everyone already has configured. Locking is local only, so two people syncing at the same moment don't coordinate through anything shared, they just each pull, merge what they see, and push. If both push at once, git's own ref update rejects the second one, and that person pulls again and retries.

This is a real gap next to jj, which keeps an operation log for the whole repository. That log records every change anyone made to the view of the repo itself, including things like which commit is the working copy's parent, and it gives jj a consistent point to reason from when several people are editing at once. sgt has no equivalent. Its sync model is pairwise and eventually consistent, closer to how git itself behaves than to jj's more centralized log. For a small team pushing every few minutes this rarely matters in practice, since forks get recorded rather than silently dropped either way, but it means sgt inherits git's race conditions on the sync path itself, even though it does better than git once the data has landed.

§10The cost of symbol-level grain

Look again at what f009 and g5c2 actually changed inside apply_discount. The agent's edit touched the tier lookup near the top of the function. Alicia's one-line fix touched a boundary check near the bottom. The two edits don't overlap by a single line. A line-based system would merge them without any trouble, since nothing about the diffs themselves collides. sgt forks them anyway, because both operations declare the same before-version of the same symbol, and that symbol is the whole function. The lines inside it never enter the comparison.

example 
def apply_discount(cart, tier):
    rate = TIERS[tier]          ← agent's edit is here
    ...
    if idx >= len(items):        ← alicia's edit is here
        idx = len(items) - 1
    return cart.total * (1 - rate)

This is the real price of choosing a symbol as the unit of history instead of a line or a hunk. Pijul and Darcs both work at line granularity, so this exact pair of edits would merge cleanly for either of them, with no fork and no rewrite step required. sgt trades that precision for a simpler identity story. A symbol has one name and one AST node to hang an identity on. A line has neither, since it is just a position that shifts every time something above it grows or shrinks. Coarser grain buys sgt a cheap, robust way to say "this is the same thing across two edits," at the cost of forking pairs of changes that a finer-grained system would have let through.

In practice this shows up most on long functions with several unrelated concerns living inside them. Splitting a large function into smaller ones lowers the odds of a spurious fork, for the same reason smaller commits lower the odds of a merge conflict in git. That's a workaround. The underlying tradeoff is still there, and it's worth knowing about before you hit it the first time on a file you didn't write.

§11Summary table

The systems in this document differ along the same handful of axes. This table lays those axes out directly, without the surrounding argument.

Reading down the identity column and the formal-guarantee column together is the fastest way to see where each system spent its effort. Pijul and lazy merging paid for a proof up front and get a narrower, more abstract unit of history in return. git and sgt spent nothing on a proof and get a unit of history that maps directly onto something a person already recognizes, a commit or a function.

§12Closing

sgt tracks history at the level of a function or a class instead of a file or a line. That choice gives it a cheap, stable identity for the things it tracks, a straightforward way to notice when two edits collide, and a fixpoint pass that keeps the rest of the repository working while a collision sits unresolved. It gives up the proofs that Pijul and lazy merging built their systems around, and it forks pairs of edits that a line-based system would have merged without complaint.

None of the other systems in this document are wrong. Darcs found the combinatorial edge of patch commutation and documented it honestly. Pijul built the category theory to fix that edge properly. jj showed that a working copy can be a commit like any other, and that a conflict can be a value instead of a crisis. Lazy merging proved a lattice join can work on partial, disordered input without a total order, and said plainly that turning that join into correct source code was somebody else's problem. sgt is that somebody else's attempt, built on a coarser unit than any of them, betting that symbol-level identity is precise enough to be useful for real code and simple enough that a team can actually run it.
