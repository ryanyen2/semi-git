=== PAGE 1: what the tool is, as a user is told ===

The tool sits on top of git. For every save (a commit, or one request to a coding agent) it keeps two things: what that save did to each function or other top-level definition, and what that save changed in what the project's own check observes. One save's change to one definition is called a step.

Later work can stand on a step in three ways, and the tool always names which:
  - "uses it": code that remains uses a definition the step created;
  - "changed it later": a later request changed a definition the step created;
  - "rewrote the same lines": a later request rewrote lines the step wrote. The tool cannot separate the two changes by itself, because the same lines carry both.

You do not tell the tool "undo this request". You ask what it would take to make a request gone, and it answers with up to three options. Nothing happens until you pick one.
  - Option 1 takes out only the steps that nothing else stands on. Steps that something stands on stay in place, whole.
  - Option 2 takes out the removal set: the request and everything that stands on it. For every other request this touches, the tool says whether it is gone entirely or partly removed, and how much of what it showed is still shown.
  - Option 3 leaves the part that stays to you or your coding agent to remove by hand, as a new save. The tool says where it is, shows the lines two requests both wrote, and gives a brief for the agent. It reruns the same comparison on that save.

The tool sees the project only through the project's own check (here check.py, which renders every page). It compares what the check shows before and after, and it knows which lines of code the check runs. So for every option it says whether what the request added to the pages is gone, and it says plainly when part of the request is code the check never runs and so cannot be confirmed. It recommends one option and gives the reason. No option leaves the check failing, and an option that changes the check itself needs your explicit confirmation.

When a request shows nothing by itself and only serves as a base for others, the tool says so and proposes which requests to ask about together.

Nothing in git history is rewritten. The result is an ordinary change in your working tree, which you commit like any other. Files the tool cannot split into definitions (templates, configuration) are treated as one piece each.

Bringing a request back works the same way in reverse. If you edited in the meantime, edits to different lines of the same function are combined automatically. Where your edit and the returning step replaced the same lines, the tool shows both versions side by side and you pick one or write a combined one; until you do, the tool does not let you commit.
