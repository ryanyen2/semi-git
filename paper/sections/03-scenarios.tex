The five scenarios below come from our own use of \sgt{} while building it and
from watching colleagues work with coding agents on repositories we maintain.
Each one is an operation a developer tried to perform, stated in the words they
used, and none of the five is available in git for the same underlying reason.
In every case the developer named a set of edits and identified that set by the
purpose the edits served, and the smallest thing git's record can name is a line
inside a commit (Figure~\ref{fig:granularity}). Every scenario has a workaround
and all the workarounds work, so our argument is about what they cost.

\subsection{``Commit this when it is done, and I do not know yet when that is''}

A developer who works through an agent still has to choose when to commit, and in
this hour every moment available to them is wrong in a different way. Committing
after each request writes a version of \sym{api.py::handle} into the permanent
history that existed for twenty-nine minutes and that nobody ever ran the test
suite against, and it files the agent's rework of the cache under the retry
commit, because the agent did that rework while adding the retry. Committing once
at the end produces a single commit holding all three requests and the rename,
which is the state Figure~\ref{fig:two-records} shows. Staging hunk by hunk
produces four clean commits and asks the developer to decide, for each of fifteen
hunks, which of those four purposes it serves. Green and Petre named these two
costs premature commitment, where a notation forces a decision before the
information the decision needs is available, and viscosity, the resistance a
notation puts up once the decision turns out to be
wrong~\cite{green1996,blackwell2003}. Git asks for the decomposition at the moment
of writing, which in a session driven by requests is a moment when the boundary
does exist and the agent is the only party holding it, and the developer's cost of
recovering it grows with every later request that touches the same functions.

\smallskip\noindent\emph{The operation.} Record the boundary the developer already stated, without
asking them to state it a second time in a different notation.

\subsection{``Change the rate limiter I built yesterday''}

The rate limiting from 14:02 used a fixed one-minute window, and three days later
it needs a sliding one. The work lands in two of the four functions the original
request produced, and the developer's first question is what the rate limiting
looked like before they touched it. Git can follow one function at a time.
\cmd{git log -L :handle:api.py} follows a function through the history by
matching a name pattern, and \cmd{git log -S} finds the commits where a given
string appeared or disappeared. Both take one function or one string at a time,
so the developer runs the first command four times, once per function they
believe was involved, and assembles the four answers themselves. The set has no
name, so nothing checks whether four was the right number. Codoban et al.\ asked
developers why they examine history and found the most common reason to be
understanding the rationale behind a piece of code~\cite{codoban2015}, and LaToza
and Myers found questions about why code is the way it is to be among those
developers report as hardest to answer~\cite{latoza2010}. The rationale in this
case was three sentences of English, typed three days ago into a window that is
now closed.

\smallskip\noindent\emph{The operation.} Name the work one request produced, see its current state
and its previous state, and change it as a unit.

\subsection{``Take the caching back out and leave the rest alone''}

The caching turned out to serve a stale price for up to sixty seconds, and it has
to go. Its six edits are spread over three files and two commits, mixed with
nine hunks belonging to three other purposes. One of the six adds a parameter to
\sym{db.py::query} and another passes it from \sym{api.py::handle}, and three
functions the rename rewrote afterwards call a helper the caching introduced.
\cmd{git revert} takes back a whole commit, so reverting either of these two
removes work the developer is keeping. The path that works is to check out both
commits, select the six hunks by hand, reverse them, and then confirm that
removing the parameter did not break \sym{handle} and that the three functions
the rename rewrote no longer call \sym{get\_cached}. That confirmation is
where the time goes, because the record contains no statement that the
\sym{db.py::query} signature and the \sym{handle} call site were changed for the
same reason. Brindescu et al.\ found that the difficulty of resolving a conflict
is predictable from properties of the change, and that how far the change reaches
is one of the properties that predicts trouble~\cite{brindescu2020}. A
hand-assembled reverse patch across two commits has exactly the properties their
model warns about.

\smallskip\noindent\emph{The operation.} Remove a named set of edits together with everything
recorded as depending on it, and leave every other edit to the same files
untouched.

\subsection{``Send just the export work to the release branch''}

An export bug fix has to ship today, and it was written on a branch that also
carries two unfinished features. \cmd{git cherry-pick} moves a commit, and the
export work is two functions in a commit that also carries part of the
unfinished retry policy. The usual answer is a temporary branch and an
interactive rebase that splits that commit, and the split has to be done again
if more export work arrives before the release. Darcs solves the part of this
problem that is about lines, because a Darcs patch carries the dependencies it
was recorded with and moving it involves no reapplication
(Section~\ref{sec:related}). The export code calls a helper introduced by one of
the unfinished features, and that call is the dependency that decides this case.
No line-level record states it, so the developer finds out when the release
branch fails to import.

\smallskip\noindent\emph{The operation.} Carry a named set of edits and its dependencies to another
branch, and be told before the operation which dependencies would come along.

\subsection{``Let someone review the rate limiter while I keep building on it''}

Code review research has converged on small, focused changes, and that finding is
why stacked pull requests exist~\cite{bacchelli2013,rigby2013}. The rate limiter was finished at 14:30 and
the caching that followed calls \sym{api.py::\_bucket}, so the two form a
stack of two layers with the rate limiter underneath. Submitting them that way
required the rate limiter to be on its own branch at 14:30, which required
knowing at 14:30 that the caching would build on it. Graphite and GitHub's
stacked pull requests automate every step after that decision, including
rebasing the upper layer when a reviewer asks for a change to the lower one
(Section~\ref{sec:related}). The decision itself belongs to the developer, it is
made before the work exists, and an agent session is the case where the layering
becomes visible only once both layers are written. Church et al.\ call this a
hidden dependency, a relationship the system relies on that the notation does not
show, and they make the point about version control
specifically~\cite{church2014}.

\smallskip\noindent\emph{The operation.} Discover the layering after the work exists, and submit one
layer while continuing to work on the layer above it.

\subsection{What the five have in common}

Every one of these five operations takes a set of edits as its argument, and the
purpose those edits served is what identifies the set. Git expresses a set of
lines, a set of files, and a set of commits, and a developer can build all five
operations out of those three. The price of building them is recovering a
decomposition that nobody recorded, which the untangling literature
has been measuring for a decade, and which stayed affordable for as long as the
person doing the recovery was the person who had written the code.
Section~\ref{sec:design} describes what we changed so that a developer can type
the argument these five operations want.
