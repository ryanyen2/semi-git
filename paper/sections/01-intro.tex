\section{Introduction}

A version control system should record the changes made by a developer in a way
that is both revisitable and reversible. Most of them therefore record the
artefact the programmer wrote, lines of code, throughout the development life
cycle, whether by recording snapshots of the codebase~\cite{git2026} or a
sequence of changes to those lines~\cite{roundy2005,pijul2024}. This is a
reasonable design choice, because code is authored by the developer, who
possesses at least a rough idea of when, how, and why it was
changed~\cite{naur1985,ko2006}. With the practice of the last few years of
writing code through large language models, where developers specify prompts in
natural language in a much vaguer form and the model translates them into a
series of code edits~\cite{sarkar2025}, we question whether this design choice
still holds.

In practice we find three places where the design philosophy of current version
control systems misfits the new workflow. First, the codebase is highly iterated.
Models make prototyping very easy, and tools like Lovable, Bolt.new, v0, and
Replit generate an entire codebase from a single prompt, marketed on the premise
that what they produce is finished software, which is arguably only true when that
software has no bugs and is tolerably aligned with what the developer was
imagining. We do not claim that writing code will be automated away in the near
future, but this reflects how capable models are at generating large chunks of
code across files, through the features of the software, iterating over interface
components, and so on, and what matters is no longer where a line of code was but
what the version of the feature was two turns ago. Across 211 million changed
lines authored between 2020 and 2024, the share associated with refactoring,
which is to say lines being moved into a better position rather than written
afresh, fell from a quarter in 2021 to under a tenth in 2024, while over those
same three years copied lines rose from 8.3\% to 12.3\% and overtook moved lines
for the first time~\cite{gitclear2025}, so a
line is now replaced faster than it settles into a position worth recording.

Second, prompts in natural language are underspecified and lack the detail that
code carries~\cite{sarkar2025}. This means there will always be large chunks of
code carrying logic that the model inferred during implementation and that the
developer only becomes aware of reactively. Barke et al.\ describe programmers in
this mode reading what comes back for the shape they expected rather than line by
line~\cite{barke2023}, Tang et al.\ found that developers often do not notice
which code a model wrote, and delete and rewrite it rather than repair it when
something is wrong~\cite{tang2024}, and among 410 developers surveyed by Liang et
al., understanding and trusting generated code was one of the most frequently
reported difficulties~\cite{liang2024}. Version control over code that never
existed in the developer's memory loses the purpose of version control, which is
that a programmer can trace back to the version they desired, because a history
can only be searched with the words that person already has.

Third, prompts are mostly constituted by what the programmer desires to do,
rather than, as they once were, by specifying the location of files and the target
of interest for the change. In that sense, developers are constructing their
theory about the codebase~\cite{naur1985} at the level of what a feature of the
software is, the components in the interface, the policy for retries, the stages
in the pipeline, none of which currently serves as the unit a version control
system records. This is the level the comprehension literature has always found
people working at: Biggerstaff et al.\ called recovering which functions
implement a named concern the concept assignment problem~\cite{biggerstaff1993},
and the feature location field exists because answering it by reading code is
expensive~\cite{dit2013}. The commit is the closest thing a version control
system offers and it is not the same unit, since Herzig and Zeller found changes
serving several unrelated purposes throughout the histories of five open source
Java projects~\cite{herzig2013}, and an agent session produces exactly that,
because a commit ends where the developer stopped to type a command and a request
ends somewhere else.

We thus describe a new version control system, which we designed to version
control the highly iterated codebase at the more semantic level of the feature,
where each version of the code is a set of edits filed across those features.
Instead of version controlling the line of code, we parse each file into its
functions and classes~\cite{treesitter} and record one edit per changed function,
where each edit names the function, the version it started from, the version it
produced, and the other functions the new code refers to. We then group those
functions into features from which ones changed in the same save, which ones call
one another, and where they
sit~\cite{zimmermann2004,ying2004,traag2019}, and label each group with the words
the developer and the agent used while the work was happening. A version is then
a set of these edits held to two rules, that no edit is included without the edits
it was built on and that each function has one included version, and the files on
disk are rebuilt by writing out the included version of every function and
leaving the text between them alone.

For example, a service that answers price quotes for a trading dashboard has a
handler, a database layer, and a set of row accessors. On Monday the developer
prompts \cmd{cache the price lookup, it takes 400ms and the price barely moves},
and the agent writes \sym{cache.py::get\_cached} and \sym{cache.py::\_ttl}, gives
\sym{db.py::query} a parameter for how long a cached price stays good so the cache
can pass one through, and changes \sym{api.py::handle} to consult the cache before
the database. That is four edits to four functions in three files, and the two in
\sym{cache.py} share no line with the one in \sym{api.py}, yet all four are filed
under one name. Over the next two days two further prompts change
\sym{api.py::handle} again, one adding a rate limit and one adding a retry policy,
and while it is adding the retry the agent goes back and reworks two of the cache's
own functions, which brings the price cache to six edits. A colleague adds a metric
for quote latency. Three weeks later the developer
finds the dashboard showing a price sixty seconds stale, so they type
\cmd{sgt revert "price cache"}. \sgt{} prints the six edits that would come out,
names \sym{api.py::handle} as the one function where later work was built on
something being removed, shows the text each change would produce, and asks before
touching anything. The rate limit and the retry policy stay, because their edits
are still included; the colleague's metric stays, because it was never in the set
coming out; and the parameter leaves both \sym{db.py::query} and
\sym{api.py::handle}, because both were in it. When the developer decides a week
later that the cache was worth keeping after all, \cmd{sgt restore} returns the
files byte for byte, because putting the six edits back is the same set arithmetic
as taking them out and nothing is replayed as a patch.

Three prices are paid for this, all of them in the first hour of use rather than
in some later edge case. Two edits to the same function made from the same
starting point are recorded as competing versions that a person has to decide
between, including the pair at opposite ends of a fifty line function that touch
no common line and that git would have merged without comment. The grouping of
edits into named requests is inferred, so it is a guess and it will sometimes be
wrong, and correcting it costs the developer a rename, a merge, or a split, none
of which moves a recorded edit. \sgt{} reads Python, TypeScript, and TSX and
versions every other file whole, at the grain git already uses, so a repository
whose interesting logic is written in Go gets nothing from \sgt{} today.

The paper makes four contributions. We characterise the mismatch between the unit
a developer using an agent decides in and the unit a version control system
records, one attempted operation at a time (Section~\ref{sec:scenarios}), in the
style of conceptual analysis Pérez De Rosso and Jackson applied to git
itself~\cite{perezderosso2013,perezderosso2016}. We describe \sgt{}'s design as
four commitments, say what each one buys and what it costs, and run the whole set
of operations on one repository (Sections~\ref{sec:design}
and~\ref{sec:walkthrough}). We state which observation would show each of our
claims to be wrong, and fix the design of the study that would produce it before
we hold its results (Section~\ref{sec:study}). We report what fifty-seven days of
\sgt{} versioning its own construction has taught us about where the design
breaks down, which is the one part of this paper whose numbers are real today
(Section~\ref{sec:discussion}).
